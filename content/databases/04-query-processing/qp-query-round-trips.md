These examples use PostgreSQL 18. SQL Fundamentals supplies the shop relations: `customers(id, name, email, city, country)`, `orders(id, customer_id, status, ordered_on, total)`, `products(id, price)` and `order_items(order_id)`. IDs join orders to customers and items to orders. Dates use `date`, IDs use `integer`, and totals use `numeric`. Each query fragment uses these names; ellipses and standalone WHERE clauses need the surrounding SELECT shown by their context.

All historical plan fragments and timings in this unit are **illustrative inputs**, not reproduced benchmarks or promises. Their row/page counts describe a hypothetical dataset; actual plans vary with statistics, indexes, settings, cache state and PostgreSQL version. Assume serial execution unless a parallel worker process is shown.

## 8. OR across different columns

```sql
-- Each alternative needs a suitable path.
WHERE customer_id = 42
   OR ordered_on = '2025-01-01'
```

Both columns are indexed, so Postgres can build a `BitmapOr` of the two index scans: 0.35 ms. Change one side to an unindexed column:

```sql
-- An uncovered branch can prevent BitmapOr.
WHERE customer_id = 42 OR total = 99.99
```

Now no index covers both alternatives, so the whole condition is a filter on a Seq Scan: 31 ms. An unindexed branch can prevent a BitmapOr covering this OR; other restrictions or an ordered or covering access path may still justify an index scan. Index both columns, or split the query into a `UNION` of two indexed queries.

## 9. N+1 queries

This one lives in application code, often generated by an ORM. The Python snippets are DB-API-style application fragments: `db.fetch(sql, parameters)` returns mutable customer objects with an `id` attribute. The `%s` placeholders are driver parameters, not PostgreSQL SQL syntax:

```python
customers = db.fetch(
    "SELECT id, name FROM customers"
    " WHERE city = %s", ["York"])
for c in customers:
    c.orders = db.fetch(
        "SELECT * FROM orders"
        " WHERE customer_id = %s", [c.id])
```

That's 1 query plus one per customer: 12,501 queries for York. Each query might take only 0.05 ms to run, but every one pays a network round trip, whose latency depends on the deployment. With a 0.5 ms round trip:

```formula
t_total ≈ n_q × (t_exec + t_RTT)
t_total ≈ 12,501 × (0.05 ms + 0.5 ms)
t_total ≈ 12,501 × 0.55 ms
t_total ≈ 6,900 ms ≈ 6.9 s
where
t_total: the total time the application spends waiting on the database
n_q: the number of queries: 1 for the customers plus 1 per customer, here 12,501
t_exec: the time the database spends running one query, here 0.05 ms
t_RTT: the network round-trip time (RTT) for one query, here 0.5 ms
ms: millisecond, a thousandth of a second
s: second
≈: approximately equal to
In words: twelve and a half thousand tiny queries add up to about 7 seconds, over 6 of them spent waiting on the network.
```

That's for data one query could return:

```python
# Fetch related orders in one batch.
rows = db.fetch(
    "SELECT * FROM orders"
    " WHERE customer_id = ANY(%s)",
    [[c.id for c in customers]])
```

Or use a JOIN. No EXPLAIN will show N+1 because each query is fast; you find it in `pg_stat_statements` (a cheap query with a huge `calls` count) or in application traces. ORMs have eager-loading options (`select_related` / `prefetch_related` in Django, `selectinload` in SQLAlchemy) to fix it.

## Key takeaways
- A BitmapOr needs access paths covering its alternatives; another usable index path may still exist.
- N+1 pays repeated query and round-trip costs; batching reduces calls but must control result size and parameter limits.
